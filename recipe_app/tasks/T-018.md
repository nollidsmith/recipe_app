# T-018 — Automate protected Hostinger production deployment

## Description

Deploy the verified production bundle automatically after a successful push to
`main`, using GitHub Actions and the protected `production` environment. Keep a
remote backup before synchronization so the previous release can be restored.

## Acceptance criteria

- [ ] A push to `main` runs the production deployment only after `procedure`, `app`, `production-bundle`, `supabase-integration`, and mandatory `supabase-preflight` checks pass.
- [ ] The workflow builds and verifies the production bundle with production variables.
- [ ] The workflow authenticates to Hostinger with environment-scoped SSH secrets and verified host keys.
- [ ] The workflow backs up the current release before syncing the new bundle.
- [ ] The workflow serializes production releases, validates the deploy path, and preserves the backup path during synchronization.
- [ ] The workflow verifies the root page, every referenced asset, and the `/recipes/new` SPA route, then restores the backup and reruns the same site smoke check if synchronization or health verification fails.
- [ ] CI and the production deployment run Playwright browser smoke tests that boot the app, verify login and password-reset experiences, load all protected route chunks, and confirm unauthenticated redirects without production secrets.
- [ ] The workflow retries transient HTTP failures, limits backup retention, and publishes success or rollback status in the GitHub Actions summary.
- [ ] Deployment contracts and runbook documentation match the workflow.
- [ ] Required checks pass and the first automated release is verified at the production URL.

## Out of scope

- Supabase migrations, Edge Functions, RLS or Storage policies, secrets, or hosted configuration changes.
- Rollback rehearsal.

## Risks / dependencies

- The GitHub `production` environment must be configured with the documented Supabase and Hostinger secrets.
- The Hostinger account must permit SSH, `rsync`, and remote archive creation at the configured deploy path.
- A first live deployment changes external production state and requires explicit release confirmation.

## Notes

- The workflow and deployment narrative were already present as uncommitted local changes when this task was opened.
- Automatic restoration is in scope; rollback rehearsal remains out of scope.
- Authenticated-flow verification remains manual because it requires a real test account or dedicated test environment.
